# M6 validation: backups, restore drill and alerts, local, 18 November 2026

**Nothing has been created on AWS.** This environment's AWS credentials were refused (`InvalidClientTokenId`). There is no production server, bucket, SES sender, alarm or DNS record.

**What M6 asks** is a restore from a *production* backup, and an alert reaching the owner. Neither is done. This record covers the rehearsal of the first, which proves the backup and restore themselves.

## The restore drill

`tools/restore-drill.sh` on the local stack, run twice, passing both times:

1. **A fresh stack and a person.** The stack started from empty volumes. A product client was registered, and a person signed up through it, confirmed their email and got an ID token. Their email, password, subject and the token's signing key (`kid`) were written down.
2. **Backup.** `deploy/backup.sh` backed up `accounts_directory`, `accounts_in`, `hydra` and `.env`, and encrypted each file to a fresh `age` key.
3. **Destruction.** `docker compose down -v` destroyed every volume. The drill checked the database volume was gone, and deleted `.env` and the plain backups.
4. **Restore.** The encrypted copies were decrypted with the private key. `deploy/restore.sh` restored all three databases, each as its own role, and the stack came back healthy.
5. **The same person signs in.** The JWKS publishes the same `kid`, so Hydra's signing key survived. The person signed in with the same password, through the same client, and got a token for the same subject, signed with the same key, with the email still confirmed.

**Control.** The same "after" checks against a fresh stack that was *not* restored fail. The drill depends on the restore.
