Steps on the servers were done by the owner, through the Lightsail console's browser SSH; the container cannot reach port 22.   - The plain-HTTP redirect could not be checked from the container, which cannot make direct connections.

- **Forms in a real browser** (Chromium): after the fix below, the forgot-password form posts with `Origin: https://staging.accounts.lotuspond.ai` and is accepted. The owner then reset a password and confirmed an email through the pages.
- **Health staging sends people to Accounts:** Health's sign-in reaches Accounts' sign-in page with a login challenge, and its sign-up reaches Accounts' sign-up page. So the client `lotuspond-health-staging` is registered.

## Found and fixed

- **No form worked in a real browser.** Under `Referrer-Policy: no-referrer`, browsers post forms with `Origin: null`, and the form check refused it. Fixed by `same-origin` ([lotuspond-ai/lotuspond-accounts#8](https://github.com/lotuspond-ai/lotuspond-accounts/pull/8)).
- **The first server stack rolled back.** Its alarms need the region's email contact, which did not exist. The runbook now creates the contact first ([lotuspond-ai/lotuspond-accounts#7](https://github.com/lotuspond-ai/lotuspond-accounts/pull/7)).
- **No certificate for 15 minutes.** The DNS records were first added proxied through Cloudflare. Caddy's first attempts also came before the records existed, and its retries then slowed down. Switching the records to DNS only, and a Caddy restart, fixed it.
- **Two DMARC records.** The runbook's template, placeholder included, was added next to the existing `p=reject` record, which left the domain with no valid policy. The template copy was deleted.
- **Health staging was never installed.** Its first boot waits for a GitHub deploy key, and none had been added. The owner added it and set the staging domain and the Accounts settings.
- **Copying the export garbled it.** Pasting the export between browser terminals turned every line into "not JSON". The runbook now packs it with `gzip | base64` first.
